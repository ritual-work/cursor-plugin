# Terminal flows — what Step 11 is when the job does not end in code

Read this from `build-flow.md` Step 11's dispatch table. A job's `terminal` (returned by
`prepare_build` at the Scope-entry gate) says what happens to its deliverable once the
user confirms it at Step 10d. `implement` stays in `build-flow.md` (11.0.0 onward). The four flows
below cover the other development terminals. Each one:

1. Starts from the deliverable file 10e wrote: `.ritual/local/build-briefs/{exploration_id}/{DELIVERABLE}.md`.
2. Runs `build-flow.md` 11.0 first (branch strategy — never commit to `main`; dirty-worktree check).
3. Commits with the `Ritual-Exploration:` trailer (11.3), syncs each commit with
   `sync_implementation` (Step 12; `decisions[]` carries what was decided, `deferrals[]`
   what was left), then continues to Step 13.

Every user-facing message begins with the build rail (`references/cli-output-contract.md`); the
last stage is the terminal's label (`Eval run`, `Execution`, `Record`, `Investigation`). Voice rules
from `SKILL.md` apply unchanged: no tool names, no step numbers, no lifecycle words on screen.

## Where each deliverable lives

Every deliverable is first written to `.ritual/local/build-briefs/{exploration_id}/` — the staging
copy, gitignored and per-user, the same place the Build Brief lands. Whether it ALSO goes into the
repo follows from what the document is for, so the confirm line states the default and takes one
word to flip it. Never ask a separate question about it.

| Deliverable | Repo home | Default | Flip |
|---|---|---|---|
| Build Brief | none — the PR body carries it | local | — |
| Eval Specification | `SPEC.md` beside the suite it describes | repo | `local` |
| Migration Plan | the repo's runbook / migration-notes directory, else `docs/migrations/` | repo | `local` |
| Architecture Decision Record | the repo's ADR directory, else `docs/adr/` | repo | — (the record IS the outcome) |
| Debugging Brief | none — `INVESTIGATION.md` goes where the repo keeps incident notes, if anywhere | local | — |
| any `deliver` document | the repo's docs directory (`docs/`, `documents/`, `doc/`), else `docs/` | local | `keep` |

A copy committed to the repo carries the attribution header, then the document verbatim:

```markdown
<!--
Generated by Ritual — {Deliverable}
Exploration: {exploration_url}
Do not remove this header; it preserves the document's lineage.
-->
```

## Confirm lines (Step 10d, when `render_gate` is unavailable)

The gate's shape is fixed — rail, `{Deliverable} ready`, the file line, one `proceed` line:

| `terminal` | `proceed` line |
|---|---|
| `generate-evals` | `proceed` — generate the eval suite from it and run it once; the spec is committed beside the suite · `local` — the same, but the spec stays out of git |
| `execute-plan` | `proceed` — execute the plan step by step, verifying each checkpoint; the plan is committed as the runbook · `local` — the same, but the plan stays out of git |
| `record-decision` | `proceed` — record it in the repo and open the PR |
| `investigate` | `proceed` — run the investigation and confirm the root cause |
| `deliver` | `proceed` — close the build; the document stays local · `keep` — commit it to the repo's docs first, then close |

The file line reads `` `{DELIVERABLE}.md` is on disk. Skim the <what to skim>, then decide: `` with
`cases, graders and thresholds` / `steps, checkpoints and rollback` / `options and the decision` /
`hypotheses and the verification steps` respectively.

## Generate evals (`generate-evals`, Eval Specification)

Landing:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Eval Specification · ▶ Eval run

Eval run

The eval specification is on disk. From here I generate the runnable suite it
describes — cases, expected outputs, graders, thresholds — in this repo's own
eval conventions, run it once, and record the baseline.

Next: a quick branch / dirty-worktree safety check, then the suite.
```

1. **Read the spec.** `EVAL-SPECIFICATION.md` § Suite Layout names the file layout, case format,
   runner and invocation; § Cases & Coverage the groups and counts; § Expected Behavior the
   reference per group; § Grading the grader per group and the thresholds. Those sections are
   binding. Where the spec says "follow the repo's existing eval conventions", look for an existing
   eval or test harness first (`eval/`, `evals/`, `__evals__`, a `test:eval` script) and match it;
   only when none exists create the layout the spec names.
2. **Generate the suite.** Write the case files (one per case, in the spec's format, grouped as the
   spec groups them), the reference outputs, the grader(s) — deterministic checks as code, any judge
   as a prompt file with the calibration sample the spec names — and the runner with the exact
   invocation the spec gives. Do NOT invent cases beyond the spec's counts; where the spec gives
   example cases, include them verbatim. Do NOT write the system under evaluation.
3. **Run it once.** Execute the runner. If it needs a secret or model pin the environment lacks, say
   exactly which and stop before running — never stub a grader to get a green run.
4. **Record the baseline.** Write the run's result where the spec's § Reporting says, or
   `eval/results/<name>/baseline.json` when it does not, and report per-group pass rates against
   the spec's thresholds.
5. **Commit** the suite, the baseline and — unless the user answered `local` at the confirm — the
   spec itself as `SPEC.md` in the suite's directory (attribution header, then
   `EVAL-SPECIFICATION.md` verbatim: it is the contract the suite implements and what a reviewer
   reads first) (11.3), then **sync** (Step 12) with a `decisions[]` entry
   per grader choice that departed from the spec and a `deferrals[]` entry per case group the spec
   asked for that could not be built (with the reason). Continue to Step 13.

Summary render:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Eval Specification · ▶ Eval run

Eval suite generated and run

  cases        {N} across {G} groups
  graders      {deterministic count} deterministic · {judge count} judge
  baseline     {passed}/{N} pass · {group}: {rate} (bar {threshold}) …

Files: {runner path}, {cases dir}, {results path}

Next: push + open PR? (y / show me what changed / abort)
```

## Execute plan (`execute-plan`, Migration Plan)

Landing:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Migration Plan · ▶ Execution

Execution

The migration plan is on disk. From here I carry out its steps in order:
each step is one change, one verification, one checkpoint you can stop at.
Nothing past the plan's point of no return runs without your go.

Next: a quick branch / dirty-worktree safety check, then step 1.
```

1. **Read the plan.** `MIGRATION-PLAN.md` § Ordered Steps is the sequence; § Verification per Step
   the check and bar for each; § Cutover names the point of no return; § Rollback the undo per step.
   The steps are binding in their order. If a step's verification is not executable from this
   environment (a production-only metric), say so and stop at that step rather than assuming it.
   Unless the user answered `local` at the confirm, the plan is the runbook of record: find where
   this repo keeps runbooks or migration notes (`docs/migrations/`, `docs/runbooks/`, `runbooks/`,
   `documents/migration*/`; create `docs/migrations/` when none) and commit `MIGRATION-PLAN.md` there
   as `<slug>.md` with the attribution header, in its own commit before step 1 runs — every checkpoint
   commit after it then has the plan it was verified against.
2. **Per step, in order:** implement the step; run its verification exactly as written; report the
   check's result against its bar. Pass → commit that step (11.3) and sync it (Step 12) like an
   implementation slice. Fail → run the step's rollback, report what was seen, and stop: the plan
   needs the user, not a workaround.
3. **[USER PAUSE] before the next step** whenever the plan names a soak time or a go/no-go, and
   ALWAYS before the step the plan marks as the point of no return. Render the checkpoint state and
   the next step's change, then wait for `go` / `pause`.
4. **Complete** = the plan's § Definition of Complete, including removal of the old path when the
   plan lists it. Continue to Step 13.

Per-step render:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Migration Plan · ▶ Execution

Step {n} of {total}: {step title}

  change       {one line}
  verified     {check} → {result} (bar {bar})
  checkpoint   {state the system is in now}
  rollback     {how this step is undone}

Next: step {n+1} — {title}. `go` to run it, `pause` to stop here.
```

## Record decision (`record-decision`, Architecture Decision Record)

Landing:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Architecture Decision Record · ▶ Record

Record

The decision record is on disk. From here I commit it where this repo keeps
its architecture decisions and open a PR for review. Nothing gets built — the
record is the outcome; any follow-up work it names becomes its own build.

Next: a quick branch safety check, then the record.
```

1. **Find the repo's decision log.** Look for an existing ADR directory (`docs/adr/`,
   `docs/decisions/`, `adr/`, `architecture/decisions/`) and its numbering and file-name convention;
   follow it. When none exists, create `docs/adr/` and start at `0001`.
2. **Write the record** as `NNNN-<slug>.md` from `ARCHITECTURE-DECISION-RECORD.md`, keeping the
   document's sections (Context, Options, Decision, Consequences, Validation & Revisit) and setting
   the status the document gives (`Proposed` unless it says `Accepted`). Add a one-line index entry
   if the directory keeps one.
3. **Commit** (11.3) and **open the PR** (11.5) with the decision statement as the title and the
   chosen option plus its rationale as the body. Do NOT implement the decision or its follow-up
   work here.
4. **Sync** (Step 12) with one `decisions[]` entry: `area` = the decision's scope, `choice` = the
   chosen option, `alternatives_considered` = the options, `rationale` from the record. Continue
   to Step 13 — the record's § Follow-up Work is the natural next job.

Summary render:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Architecture Decision Record · ▶ Record

Decision recorded

  {NNNN-slug.md} — {decision statement}
  status   {Proposed | Accepted}
  chosen   {option}

Next: push + open PR? (y / show me what changed / abort)
```

## Investigate (`investigate`, Debugging Brief)

Landing:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Debugging Brief · ▶ Investigation

Investigation

The debugging brief is on disk. From here I reproduce the issue, test its
hypotheses in the order the brief ranks them, and write down what the
evidence says — confirmed cause, or what was ruled out and why.

Next: a quick branch / dirty-worktree safety check, then reproduction.
```

1. **Read the brief.** `DEBUGGING-BRIEF.md` § Hypotheses is the ranked list to test; § Symptoms and
   § Field Reproduction say how to reproduce; § Verification Checklist says what proves a cause.
   Test hypotheses in the brief's order; do NOT start with the one that is easiest to code around.
2. **Reproduce first.** Get the failure to happen locally or against the environment the brief
   names. If it cannot be reproduced from here, say what is missing (data, access, a log) and stop —
   an unreproduced fix is a guess.
3. **Per hypothesis:** the test that would confirm or refute it, the evidence observed, the verdict.
   Stop at the first confirmed cause; keep the refuted ones with their evidence.
4. **Write `INVESTIGATION.md`** next to the brief (`.ritual/local/build-briefs/{exploration_id}/`)
   and, when the repo keeps incident or debugging notes, a copy where it keeps them: reproduction,
   hypotheses with verdicts and evidence, confirmed root cause, the proposed fix and its risk from
   the brief's § Proposed Fix, updated with what was learned. Commit it (11.3).
5. **Do not implement the fix in this flow.** Offer it as the next job: `fix` → start a new
   `/ritual-build` for the fix with `INVESTIGATION.md` as context (Step 13 names it as the
   suggestion); `done` → stop here.
6. **Sync** (Step 12) with a `decisions[]` entry for the confirmed cause (`area` = the failing
   component, `choice` = the cause, `alternatives_considered` = the refuted hypotheses) and a
   `deferrals[]` entry for the fix. Continue to Step 13.

Summary render:

```text
Ritual build
✓ Scope · ✓ Discovery · ✓ Recommendations · ✓ Debugging Brief · ▶ Investigation

Root cause {confirmed | not confirmed}

  reproduced   {yes — how | no — what was missing}
  cause        {one line, or "none of the {n} hypotheses held"}
  ruled out    {hypothesis} — {evidence} …
  fix          {proposed fix} · risk {low | medium | high}

Next: `fix` to start the fix as its own build, `done` to stop here.
```

## Deliver (`deliver`, any document job)

Nothing runs: the document is the outcome. `proceed` goes straight to Step 13 with the document in
its staging copy. `keep` first commits it where this repo keeps its docs (`docs/`, `documents/`,
`doc/`; create `docs/` when none) as the document's name in kebab-case (`codebase-orientation-brief.md`,
suffixed with the exploration slug when that name is taken), attribution header first, on a branch
per 11.0 with the `Ritual-Exploration:` trailer (11.3) — then Step 13. No PR is opened here; Step 13
offers it like any other commit.
